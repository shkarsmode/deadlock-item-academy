# Руководство автора учебного контента

Этот документ обязателен для всех, кто пишет контент Deadlock Item Academy (люди и агенты).
Схема типов: `src/app/content/content.model.ts`. Словари тегов: `src/app/content/vocab.ts`.
Проверка: `npm run content:validate -- --only <часть пути к своему файлу>`.

## 1. Главный критерий

Ученик должен научиться **принимать решения о покупке**, а не заучивать билды. Каждый текст отвечает на вопрос
«какую проблему решает предмет и когда он хуже альтернатив». Точность важнее объёма: 100 точных ситуаций лучше 1000 выдуманных.

## 2. Источники правды

1. Нормализованные данные клиента 6864 (18.11.2026): `public/data/game/items.json`, `heroes.json`, `meta.json`.
2. Досье для авторов (сгенерированы из тех же данных, удобно читать): `items-all.md`, `items-index.md`, `heroes.md`, батчи `items-batch-N.md`
   (путь сообщается в задании).
3. Иконки предметов: `public/game/items/<key>.webp`, способностей: `public/game/abilities/<key>.webp`.
4. Патчноуты: последний крупный геймплейный патч 30.10.2026 (Halloween 2026 + Gameplay Update) и Minor Update 04.11.2026.

Нельзя опираться на память о старых версиях игры. Если механики нет в данных, это не факт.

## 3. Статусы утверждений

Каждое утверждение (`Claim`) имеет статус. Если статус не указан, считается `expert`.

| status | когда ставить |
| --- | --- |
| `data` | Прямо следует из официальных данных клиента: описание, статы, стоимость, активный или пассивный, imbue, компоненты. |
| `expert` | Ситуационная рекомендация, логично выведенная из механик. Должна быть обоснована в тексте. |
| `stat` | Статистическая закономерность (pick rate, win rate). Никогда не подавать как причину. Формулировка: «чаще покупают», «коррелирует». |
| `unverified` | Правдоподобно, но не подтверждено данными (взаимодействия, стакание, точные пороги). Приложение покажет предупреждение. |

Запрещено: придумывать числа, стакание эффектов, взаимодействия с конкретными способностями, если этого нет в данных.
Если очень хочется сказать о взаимодействии, которого нет в данных, ставь `unverified` и формулируй осторожно.

## 4. Проверенные механики (можно использовать со статусом `data`)

- Магазин: T1 800, T2 1600, T3 3200, T4 6400 душ. **T5 (9999) - легендарные предметы только для режима Street Brawl.** В обычных матчах их нет: не используй их нигде.
- Улучшение из компонента: компонент поглощается, его стоимость засчитывается. Цена для игрока = стоимость - стоимость имеющегося компонента
  (валидатор считает это сам).
- Бонусы вложений в категорию (souls, потраченные на предметы категории):
  пороги 800 / 1600 / 2400 / 3200 / **4800** / 6400 / 8000 / 11200 / 16000 / 22400 / 28800.
  Weapon: +% урона оружия (9, 12, 15, 18, **46**, 54, 62, 74, 86, 100, 115).
  Vitality: +% здоровья (9, 12, 15, 20, **38**, 42, 46, 50, 54, 60, 66).
  Spirit: +духовная сила (7, 11, 15, 19, **38**, 45, 52, 59, 66, 75, 100).
  На 4800 бонус резко растёт: отсюда группы «Spirit 4.8k / Weapon 4.8k / Vitality 4.8k» в популярных билдах.
- Дополнительные слоты предметов открываются за уничтожение вражеских Walker (первый, второй, все). Точное базовое число слотов в данных не указано, его не называем.
- Imbue: при покупке игрок выбирает способность. Сборка может хранить «Imbue Target» (подсказку). Виды:
  `imbue_modifier_value` (меняет параметры способности: Mystic Expansion, Compress Cooldown, Duration Extender),
  `imbue_active` (срабатывает при использовании способности: Quicksilver Reload, Surge of Power, Mercurial Magnum, Ballistic Enchantment, Mystic Reverb),
  `imbue_active_non_ult` (нельзя на ультимейт: Echo Shard). Некоторые способности в клиенте помечены «Cannot be imbued», список в данных не опубликован.
- Улучшения imbue-предметов меняют правило: Superior Cooldown (из Compress Cooldown) и Superior Duration (из Duration Extender) действуют на все способности, а не на одну.
- The Broker: в середине матча открывается магазин порчи. Предмет T3/T4 можно «испортить» (Corrupted): он сильнее, но получает случайный минус, который определяется на каждый матч. После restock можно испортить ещё один предмет.
- Активации: `press` (нажать, часто с целью), `instant_cast` (мгновенно), `instant_cast_toggle` (переключатель).
- Ограничения из описаний: Dispel Magic и Unstoppable нельзя использовать под Stun или Sleep. Dispel Magic снимает только неультимативные эффекты.
  Metal Skin даёт иммунитет только к пулям. Decay не может убить и не активирует эффекты предметов.
- Лечение режется предметами и способностями (Healbane, Toxic Bullets, Decay, Crippling Headshot, Napalm T3 у Infernus, Crow Familiar T1 у Vindicta).
  Как именно складываются разные источники анти-хила, в данных не указано, это `unverified`. Известно только из патча 30.10.2026: несколько Healbane от разных игроков стакаются с убывающей отдачей.

## 5. Стиль

- Язык: русский. Названия предметов и способностей пиши **официальными английскими** именами, как в клиенте пользователя (игра на английском):
  Counterspell, Dispel Magic, Crow Familiar, Assassinate. Русское название можно дать один раз в скобках, если это помогает.
- **Никогда не используй длинное (U+2014) и среднее (U+2013) тире.** Только обычный дефис «-», запятая, двоеточие или два предложения. Валидатор это проверяет.
- Без эмодзи, без HTML. Выделение не нужно, интерфейс оформит сам.
- Коротко и конкретно. `job` - одно предложение. `simple` - 2-3 предложения для новичка. `detail` - 3-6 предложений с механикой и нюансами.
- Плохо: «Предмет даёт +X% характеристики». Хорошо: «Решает проблему X. Бери, когда враг делает Y. Помогает сделать Z, но не решит W».
- Числа бери только из данных и только когда они важны для решения. Предпочитай формулировки, которые не устареют от мелкого баланса.
- Обращайся к игроку на «ты».

## 6. Предметы (`content/items/*.json`, массив `ItemContent`)

Обязательные поля: `key, roles, counters, job, simple, detail, buyWhen (1+), skipWhen (1+), mistakes (1+), alternatives (1+), example, status`.
Для активных предметов обязательно `activeUse {when, saveFor, tooEarly}`. Для imbue-предметов обязательно `imbue {goodTargets, badTargets}`.
`iconCue` - короткая визуальная подсказка: что нарисовано на иконке и как это связано с функцией (открой файл иконки и посмотри).
`doesNotSolve` - частые заблуждения («не спасает от спирит-урона» для Metal Skin).
`status`: `expert`, или `needs-review`, если сомневаешься в нескольких пунктах.

## 7. Сценарии (`content/scenarios/*.json`, массив `Scenario`)

Сценарий - реалистичная ситуация из матча с 3-5 правдоподобными вариантами.

- `kind`: `buy` (что купить), `diagnose-buy` (сначала назвать проблему, потом купить; нужен блок `diagnosis`), `active-timing` (когда и что нажать;
  варианты - действия `action`), `imbue` (на какую способность назначить; варианты - `ability`, и imbue-предмет должен быть в `owned` или в `sources` как `item:<key>`),
  `surgery` (в `startBuild` 4+ предметов, `swaps` 1-3, варианты - предметы для замены), `sell` (что продать; варианты из `owned`).
- `souls` реалистичны для фазы: laning 800-3500; early-mid 1600-5000; mid 3200-7000; late 6400-15000. `owned` соответствует фазе.
- Варианты правдоподобны: решают похожую проблему, но хуже по условиям (тип урона, бюджет, тайминг, имеющиеся предметы, состав врагов).
  Не добавляй заведомо бессмысленных вариантов.
- Оценка: `score` 0-100 и `verdict` по шкале: best 80-100, good 60-79, ok 40-59, weak 20-39, bad 0-19. Хотя бы один `best`.
  Несколько хороших решений - нормально, тогда объясни компромисс.
- Предмет дороже доступных душ (с учётом компонентов) не может быть `best` или `good`.
- `why` объясняет оценку в этих условиях. `betterWhen` - при каких условиях этот вариант был бы лучше (обязательно для good/ok/weak).
- `situation` описывает, что происходит, но **не называет лучший предмет** (валидатор проверяет английское и русское название).
  `symptoms` - наблюдаемые признаки для сложного режима («ты умираешь за 2 секунды после того, как тебя замедлили»).
- `principle` - одно короткое правило для запоминания. `mechanics` - ключевые механики (обычно `data`). `tree` - дерево решения:
  проблема, возможные решения, ограничения, выбор, последствия.
- `difficulty`: 1 - одна очевидная угроза и явная проблема; 2 - явная проблема, 2 близких варианта; 3 - проблему надо вывести из 2-3 фактов;
  4 - конкурирующие угрозы и ограничения (бюджет, слоты, имеющиеся предметы); 5 - неполная информация, только симптомы, нужна глубокая механика.
- `dims` - какие знания тренирует: `situation`, `counter`, `build`, `synergy`, `active`, `mechanics`, `effect`.
- `sources`: `item:<key>`, `ability:<key>`, `hero:<key>`, `patch:2026-10-30`, `build:<id>`, `stat:<что>`, `expert:<кратко>`.
- `id`: латиница, цифры и дефис, с префиксом темы: `vin-def-001`, `gra-tf-004`, `gen-heal-010`.
- Вариативность: не переставляй слова. Хорошая вариация меняет условия решения: бюджет, уже купленные предметы, состав врагов, фазу, тип урона.

## 8. Курсы героев (`content/heroes/<hero_key>.json`, объект `HeroCourse`) и разборы билдов (`content/builds/*.json`, `BuildAnalysis`)

- Курс состоит из модулей: цель, урок (2-6 коротких абзацев), ключевые выводы (2-4), список предметов, теги сценариев для тренировки, фокус знаний.
- Не копируй курс Vindicta для Graves с заменой имени: механики героев разные.
- Разбор билда критичен: что в билде сильно, что спорно, что зависит от игры. Для каждого предмета 10 пунктов (`BuildItemAnalysis`).
- Не утверждай, что билд идеален. Отличай «автор билда так считает» (аннотации) от проверенной механики.

## 9. Проблемы (`content/problems/*.json`, массив `ProblemEntry`)

Поиск по проблеме: «враги сильно лечатся». Решения группируются по типу (снизить лечение, убить быстрее, ...), с оговорками.

## 10. Проверка перед сдачей

1. `npm run content:validate -- --only <часть пути к своему файлу>` - 0 ошибок в своих файлах.
2. Перечитай каждое утверждение: можно ли подтвердить его досье? Если нет - `unverified` или удалить.
3. Нет длинных и средних тире, нет HTML, нет T5-предметов, нет названия лучшего ответа в `situation`.
